# Порты и направление зависимостей: постановка

**Это не спецификация**, а рамка для решения: две развилки открыты, и пока они
открыты, спеку писать не на чем. Строка реестра: [backlog.md](backlog.md).

## Что не так

- Слой `foundation` внизу стека означает, что домену **разрешено** зависеть на
  инфраструктуру: там лежат `MachineStore`, `Workspace`, `NetworkClient`,
  `WriterLock`. В Clean Architecture правило обратное — зависимости направлены
  внутрь, к домену, а инфраструктура зависит от него.
- Отдельного слоя домена вообще нет: 13 сущностей породы `data` размазаны по
  шести рангам, потому что стек упорядочен по стадии конвейера, а не по
  зависимости. Сказать «вот это домен, и он ни от чего не зависит» нечем.
- Карта не умеет выразить различие порт/адаптер: ни породой, ни классом связи,
  ни пометкой. Это не ошибка именования — назвать нечем.
- CLAUDE.md §3 формулирует DIP верно, стек кодирует обратное. Сгенерированный из
  такого стека контракт import-linter **запретит** переход к CA, а не обеспечит его.

## Цена (измерено, не оценено)

| Вариант | Нарушений направления |
|---|---|
| как сейчас | 0 |
| полный разворот стека | 14 из 15 |
| **только `foundation` наверх** | **4** |

Три нарушения из четырёх ведут на один адресат — `NetworkClient`
(из `AcquisitionAct`, `Enrichment`, `QueryLayer`). Четвёртое —
`QueryLayer → DerivationManifest`.

## Развилки

1. **Гранулярность порта.** Один порт на все исходящие вызовы или отдельные для
   скачивания и для вызовов моделей? Критерий: различаются ли у них политика
   повторов и режимы отказа. Ответ даст перенос OCR-конвертера из старого
   проекта — там сетевой клиент уже боевой, а не спроектированный.
2. **`QueryLayer → DerivationManifest`.** Зависимость от механизма или чтение
   значения? Если значение — ребро меняет класс, и четвёртый порт не нужен.

## Ограничения реализации (измерено)

- Словарное значение и его первый носитель вводятся **одним коммитом**: порода
  без носителя валит тест dead-vocabulary, хотя `validate()` при этом молчит.
  Подготовить словарь заранее нельзя.
- Перестановка слоёв — данные: перенос строк, ноль правок кода.
- Проверка направления уже существует (20 строк) и покрыта мутациями; её
  изменение не пройдёт молча.

## Порядок работ

1. **Предохранители для разведочного кода — раньше всего.** Пока `mkdir src`
   даёт 36 ошибок, проверить работу на настоящем коде нельзя.
2. Класс связи «реализует порт» + первый порт → закрывает 3 нарушения из 4.
3. Решение по манифесту → закрывает четвёртое.
4. Подъём `foundation` наверх.
5. **Контракт import-linter — последним.** Сгенерированный раньше, он
   зацементирует направление, которое никто не проверял на живом коде.

## Что считать успехом

Ноль нарушений направления при `foundation` наверху; домен не зависит ни на один
адаптер, только на порты; гейт и мутации зелёные. Ориентир объёма — прецедент
`05b5dac` (добавление словарного блока с проверкой): 281 рукописная строка, из
них новой логики около 20.

## Чего гарантировать нельзя

Ни один затрагиваемый механизм не видел живого кода — по правилу самого проекта
это гипотезы. Ноль нарушений сегодня ничего не подтверждает: раскладку по слоям
делал ассистент, и она зелёная именно поэтому. Первый настоящий модуль может
показать, что граница слоя проведена не там, а гранулярность порта выбрана
неверно. Планировать с допущением пересмотра, а не вопреки ему.
