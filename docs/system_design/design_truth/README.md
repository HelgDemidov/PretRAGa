# Контроль архитектурной истины (design truth)

## Что это за система

Курируемая машиночитаемая модель архитектуры + автоматическая проверка того, что
репозиторий ей соответствует. В профессиональной терминологии это связка:
**architecture-as-code** (модель как код — класс Structurizr/C4, у нас — вокруг
сущностей данных и слоёв) + **проверка архитектурного соответствия**
(architecture conformance checking) + **предотвращение дрейфа** (drift
prevention); сами проверки — **архитектурные fitness-функции**. Название
«система контроля архитектурной истины» сути соответствует.

Главный принцип: **машина никогда не переписывает истину.** Код сверяется с
картой, расхождение падает громко; разрешение — всегда человеческое решение:
починить код или осознанно править карту. Истина, автоматически обновляемая из
кода, была бы зеркалом — а зеркало ничего не сдерживает.

## Функциональные блоки

| Блок | Подход | Носитель |
|---|---|---|
| Единый источник истины | architecture-as-code | [entity_map.yaml](entity_map.yaml) — ЕДИНСТВЕННЫЙ рукописный файл системы и единственный канал изменений: сущности, атрибуты, связи, термины, их определения (обязательное поле `definition`), ВСЕ закрытые словари (породы, статусы, пометки, типы и классы связей, триггеры, слои, группы) и сквозные конвенции (блок `conventions`); след решений (облегчённый ADR) — в [../architectural_vision.md](../architectural_vision.md) §9. В коде не остаётся ни одного имени из номенклатуры — генератор ветвится по СВОЙСТВАМ значений (`settled`, `requires_trigger`, `class`), а не по их именам, и это закреплено тестом |
| Обязательства по породам | typed classification | у каждой сущности есть `kind` из закрытого словаря, и порода несёт проверяемые обязательства (якорь, идентичность, версия, размещение, атрибуты), а не ярлык. Новая порода или новый тип связи — ЗАПИСЬ в карте, а не правка скриптов |
| Направление зависимости | layered architecture | блок `layers` — УПОРЯДОЧЕННЫЙ словарь, поле `layer` у каждой сущности; связь класса `dependency` вверх по стеку = ошибка сборки. Отсюда растёт контракт import-linter, как только появятся якоря кода: слой модуля равен слою его сущности |
| Генерируемые представления | living documentation | [entity_map.md](entity_map.md) (словари карты + сводная межгрупповая схема + проекции по группам + полный граф + таблицы атрибутов + реестр плейсхолдеров + реестр открытых обязательств) и [entity_glossary.md](entity_glossary.md) (словарь: конвенции + порода и определение каждой сущности); производит [entity_map_build.py](entity_map_build.py); руками не правятся — устаревание и ручная правка ловятся проверкой свежести |
| Проверка соответствия | fitness-функции, статический анализ | [entity_map_check.py](entity_map_check.py); с появлением кода: дифф pydantic-моделей, контракт слоёв import-linter, генерируемый из карты (policy-as-code) |
| Трассировка | якоря код↔сущности | поле `implements` в карте + режим `--impact` |
| Петля предотвращения дрейфа | три выхода одной проверки | хук сессии (`.claude/settings.json`) → локальный гейт → CI |

## Как это работает — по шагам

1. **Фоновый контроль.** Любая правка файла под `src/`, `docs/system_design/`
   или словаря `*.yaml`/`*.json` будит хук сессии (`.claude/settings.json`),
   который запускает [entity_map_check.py](entity_map_check.py) `--hook`:
   в сессию приходит отчёт — статус проверок и какие сущности задеты; правка
   файлов самой истины помечается отдельным предупреждением («это дизайн-решение,
   а не способ заглушить проверку»). Информационные строки — совет; ошибки
   соответствия хук возвращает блокирующим решением — исполнитель обязан вернуть
   систему в зелёное состояние либо явно поднять проблему, прежде чем продолжать.
2. **Изменение архитектуры.** Единственный канал — правка
   [entity_map.yaml](entity_map.yaml): состав сущностей, атрибуты, связи, термины
   и их определения (поле `definition`, обязательное — сущность, которую нельзя
   определить прозой, не готова войти в истину). Затем
   [entity_map_build.py](entity_map_build.py) валидирует граф (висячие связи,
   изолированные сущности, отсутствие триггера там, где статус его требует,
   сущности без определения, значения вне закрытых словарей, нарушенные запреты
   пород, зависимость вверх по слоям) и пересобирает оба представления. Сквозные
   конвенции редактируются там же — блок `conventions` в начале карты; вся
   номенклатура — блоки `kinds`, `statuses`, `marks`, `relation_classes`,
   `relation_types`, `triggers`, `layers`, `groups`.

   **Строгость схемы — тоже данные.** Обязательства породы это шесть слов в её
   строке блока `kinds`, и каждое принимает `optional`. Ослабить требование —
   одна правка одного слова, без правки скриптов; проверка исчезает вместе с
   требованием. Удаление сущности забирает её атрибуты (они вложены в её блок),
   но НЕ забирает связи: чекер назовёт каждую висячую поимённо, поэтому
   наполовину удалить нельзя. Цена удаления — блок плюс степень сущности в
   графе; медиана по карте — четыре связи.
3. **Проверка соответствия.** [entity_map_check.py](entity_map_check.py) без
   аргументов: целостность карты (включая обязательность определений), свежесть
   обоих генерируемых представлений (ловит и забытую перегенерацию, и ручную
   правку сгенерированного), разрешимость якорей кода, поиск кода-сироты, реестр
   открытых обязательств. Ненулевой код выхода = расхождение; лечится шагом 2
   либо правкой кода.

   Две ступени намеренно разделены. **Ошибка** — карта поломана или сущность
   нарушает ЗАПРЕТ своей породы: это ошибка классификации, чинится без
   дизайн-решения, поэтому блокирует. **Открытое обязательство** — не закрыто
   ТРЕБОВАНИЕ породы (нет идентичности, версии, размещения): закрыть его значит
   решить, чем сущность опознаётся или где она лежит, — решение человеческое,
   поэтому оно считается и называется, но не блокирует. Реестр без блокировки
   честнее, чем блокировка, которую снимают, приписав сущности выдуманный ключ.
4. **Локализация изменения.** [entity_map_check.py](entity_map_check.py)
   `--impact <файлы>` — список задетых сущностей по якорям.
5. **Жёсткие ворота.** Та же проверка встаёт в локальный гейт (с появлением
   `src/`) и в CI (с появлением `.github/workflows/`) — там она блокирует.

Зеркало карты в графовой базе знаний (MCP-сервер `memory`) — производное для
запросов из сессий; пересобирается из YAML, истиной не является.

## Как это запускать

Чекер отдельно: `.venv/bin/python docs/system_design/design_truth/entity_map_check.py`.
Пересборка представлений: тот же путь, но `entity_map_build.py`.
Тесты инструментов: `.venv/bin/python -m pytest docs/system_design/design_truth`.
Все четыре ворота разом — команда локального гейта (см. `CLAUDE.md` §10); те же
четыре шага выполняет CI (`.github/workflows/ci.yml`), и при расхождении команда
сверяется с ним, а не наоборот.

**Что будет, если удалить сущность:** `entity_map_check.py --removal-impact <Id>
[<Id> ...]` — сухой прогон. Печатает связи, которые повиснут; сущности, которые
станут изолированными; значения словарей, оставшиеся без носителей; и как
изменится число открытых обязательств. Ничего не пишет: правка остаётся за вами.

## Почему код лежит рядом с документами

[entity_map_build.py](entity_map_build.py) и
[entity_map_check.py](entity_map_check.py) — инструменты именно этих артефактов:
порознь они бессмысленны, а вместе переезжают безопасно (пути внутри папки
относительные). Условие соседства: локальный гейт линтует и проверяет типами
эти файлы наравне с `src/`.

## Известные дыры (честный реестр)

- Проверяется ГРАФ, но не ПРОЗА: расхождение определений со связями не ловит ничто. Одиннадцать фактов, живших только в прозе, подняты в граф; три остались непредставимыми, и не по недосмотру: «якоря только в оригинале» — отрицание, ребром не выражается (живёт атрибутом `original_only`); «очереди склеек» и «уверенности» из определения машинного хранилища не имеют сущностей вовсе, а очередь исключений — процесс, которому порода запрещает размещение.
- Конвенции остаются непроверяемой прозой: правило «один писатель» проверить нечем, поля писателя нет. Хуже — конвенция идентичности теперь записана дважды, прозой в `conventions` и обязательством `identity` в `kinds`; два места, одно правило.
- Стек слоёв нагружен слабо: класса `dependency` в карте 10 связей из 85, поэтому проверка направления подтверждает немногое. Класс `governance` не ограничен намеренно (там ребро смотрит против зависимости кода) — если его когда-нибудь ограничат, первым делом пересмотреть слой `Reconciliation`.
- Покрытие чекера меряется как 20%, но это артефакт: его тесты гоняют его подпроцессом, которого coverage из родительского процесса не видит. Настоящая цифра выше и неизвестна.
- Сверка кода с картой (якоря, дифф моделей, контракт слоёв) доказана на полигоне, но не на живом коде — первый настоящий экзамен системы: walking skeleton. Дифф моделей упрётся в потолок: у атрибутов есть имя и статус, но нет типа и кардинальности, поэтому сверяться будут множества имён.

## Два реестра: что согласовано, но не закрыто

Ничто согласованное, но не расписанное, не теряется — и на это работают два
реестра в конце [entity_map.md](entity_map.md):

- **Реестр незакрытого** — КАЖДЫЙ атрибут, чей статус не объявлен закрытым
  (`settled: false`), а не только плейсхолдеры: ждущие измерения и отложенные за
  MVP тоже согласованы и тоже не расписаны. Членство решает флаг самого статуса,
  поэтому новый статус попадает в реестр тем, что объявлен, а не тем, что о нём
  вспомнили. Статус с `requires_trigger` без триггера не проходит валидацию.
- **Реестр открытых обязательств** — требование породы, которое сущность не
  закрывает. Не блокирует: закрытие каждой позиции есть дизайн-решение.

## Сужение: что стоит удалить

Схема закрыта для сужения не запретом, а **видимостью**: удалить можно почти всё,
но ни одно удаление не проходит молча. Обнаружение полностью автоматическое и
называет каждую строку поимённо; починка — всегда ручная, потому что машина не
переписывает истину.

| Что убираем | Цена | Что скажет система, если забыть хвосты |
|---|---|---|
| атрибут | 1 строка | ничего — у атрибута нет иждивенцев; но снятая пометка откроет обязательство |
| связь | 1 строка | `isolated entity`, если она была последней у сущности |
| **сущность** | блок + её связи: медиана **4**, максимум 12 | `relation endpoint not a defined entity` на каждую висячую |
| значение словаря | запись + все носители: от 1 до 83 | `unknown kind/status/layer/...` на каждый носитель |
| обязательство породы | **одно слово** `required` → `optional` | — ослабление всегда законно |
| словарный блок целиком | невозможно | `missing top-level <блок> block` |

Два «пола» держат схему от вырождения в обе стороны: значение словаря без единого
носителя и носитель без значения в словаре одинаково валят сборку. Раздуть схему
мёртвыми значениями или выпотрошить её наполовину нельзя.

Дорого здесь не удаление, а **переназначение**: убрать сущность — около пяти
правок, убрать значение словаря — столько, сколько у него носителей. Дешевле
всего ослабить строгость: обязательства породы это шесть слов в её строке блока
`kinds`, и каждое принимает `optional`.

## Где что искать

- **Плоский перечень всех сущностей** — «Указатель сущностей» в начале
  [entity_map.md](entity_map.md): имя, код, порода, слой, группа, счётчики.
  Единственный несгруппированный список; остальные разложены по осям.
- **Вся номенклатура модели** — «Словари карты» там же: породы с обязательствами,
  типы связей с классами, триггеры, статусы, пометки, группы. Плюс слои отдельным
  разделом, потому что у них есть порядок.
- **Определения сущностей прозой** — [entity_glossary.md](entity_glossary.md).
